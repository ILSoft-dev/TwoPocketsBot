# Two Pockets — Telegram-бот учёта финансов

Бот для учёта доходов и расходов: текст, голос, фото чека (сумма), плюс
вопросы на естественном языке. Стек: aiogram 3, Google Sheets (сами
транзакции), Supabase/Postgres (метаданные + кэш-зеркало транзакций), Groq
(LLM + Whisper + Vision), Redis (FSM-состояния + кэш чтения Sheets), Render +
UptimeRobot.

## ✅ Чеклист перед тем, как считать деплой сделанным

1. Repository и Branch в Render → Settings указывают ровно на тот репозиторий/ветку, куда реально запушено.
2. Если менял Python/`requirements.txt` — сделал **Clear build cache & deploy**, не обычный редеплой.
3. Все переменные окружения из `.env.example` заданы в Render → Environment.
4. `/health` отвечает `ok`.
5. Отправил боту одно тестовое сообщение и получил на него ответ.

## ⚠️ Главное правило ввода

**Всегда указывай валюту рядом с суммой.** Без этого бот не может отличить
сумму от количества/массы.

- ✅ `кофе 150р`, `зарплата 100000₽`, `такси 350р`, `2кг конфет 30р`
- ❌ `сахар 5` — непонятно: 5 килограмм или 5 рублей?

Поддерживаемые обозначения валюты: `р`, `руб` (и любые склонения — «рубля»,
«рублей», «рублях»), `₽`, `byn`, `br`, `$`, `usd`, `€`, `eur`. Рубли/копейки
можно диктовать раздельно голосом: «8 рублей 43 копейки» → 8.43; если Whisper
потерял слово «копеек» («8 рублей 43») — тоже распознаётся, если число из
1-2 цифр стоит в самом конце фразы.

### Количество и единицы измерения

Если в сообщении узнаётся количество/единица — записывается отдельно от
суммы (см. «Количество»/«Единица» в структуре Google-таблицы ниже):

- `Два мороженых 50р` → количество 2, единица не указана (штучно)
- `Килограмм моркови 30р` → количество 1, единица «кг»
- `5 литров масла GM 10w40 45р` / `Масло Опель 5л 45р` → количество 5,
  единица «л» (единица распознаётся и с пробелом, и слитно с числом)

Распознаются единицы кг/г/л/мл/шт/уп (с падежами) и числительные словами
один-двадцать. Если количество не удалось распознать — просто не
заполняется, транзакция всё равно сохраняется по сумме и комментарию.

### Фото чека

Vision-модель (`qwen/qwen3.6-27b`) сейчас распознаёт **только итоговую сумму
чека** («Итого»/«К оплате»), не построчный состав покупок. Результат
записывается одной строкой в одну категорию — так же, как ручной ввод текста
без уточнения товаров. Построчного разбора по позициям (каждый товар — своя
цена и своя категория) в боте пока нет.

## Вопросы на естественном языке

Кроме ввода трат, боту можно задать вопрос по накопленным данным — ответ
считает код по данным из Sheets/зеркала, LLM (`groq_client.parse_question`)
только разбирает вопрос в структурированный запрос
(intent/категория/товар/машина/период), без «фантазии» в цифрах. Поддержаны
ровно эти виды вопросов (см. `insights.py`):

- **Траты/доходы**: «сколько я потратил на продукты в июле?», «сколько
  заработал в этом месяце?» — сумма в деньгах + число подходящих записей
- **Пробег**: «какой пробег у опеля за август?» — дистанция за период по
  показаниям одометра
- **Когда** (дата последнего подходящего события за всю историю, не
  ограничено периодом): «когда я менял масло на опеле?», «когда последний
  раз покупал кофе?», «когда заправлял опель?» — для авто-трат ищет по
  листу «Авто» конкретной машины, для остального — по общим Транзакциям
- **Сколько штук/кг/литров** (не деньги!): «сколько мороженого я купил?»,
  «сколько литров масла купил в этом месяце?» — суммирует поле
  «Количество», отдельно по каждой единице измерения; старые записи без
  количества не приравниваются к 1 — либо честно говорит «нечем посчитать»,
  либо считает по тем, где количество есть

Вопрос про конкретный товар («сколько на мороженое?») ищется подстрокой (с
запасом на падежные окончания) в описании транзакции, а не по названию
категории — если товар назван явно, категория для поиска игнорируется.

**Не поддержано** (несмотря на то, что раньше значилось в планах): подсчёт
числа покупок отдельно от суммы («сколько раз покупал...»), средний чек,
автоматическая кластеризация похожих описаний в товарные группы,
сравнение с предыдущим периодом. Если понадобится — это отдельная фича,
трогающая и промпт `parse_question`, и `insights.py` (см. `DEVELOPER_GUIDE.md`,
раздел про добавление нового intent).

## Категоризация

Три слоя, в порядке приоритета:

1. **Жёсткие правила** (`config.AUTO_FORCE_KEYWORDS`/`TRANSPORT_FORCE_KEYWORDS`,
   применяются через `config.forced_category`, вызывается из
   `input_handler.resolve_expense_category`) — специфичные слова («бензин»,
   «масло», «такси»...) всегда попадают в свою категорию, независимо от
   того, что раньше выучила память или что угадает LLM.
2. **Память** (`category_map` в Supabase, longest-match — самое длинное
   совпавшее слово побеждает) — если раньше уже выбирал категорию вручную
   для похожего слова.
3. **Groq LLM** — фоллбэк, если ни правило, ни память не сработали; если и
   LLM не уверена — бот спросит категорию кнопками (выбор запоминается).

Траты категории «Авто» дополнительно получают структурированный разбор —
машина (по названию из зарегистрированных), тип (Заправка/ТО/Ремонт/Прочее
по ключевым словам), пробег (если упомянут «... км»).

**Переименование категории** (`/categories`) обновляет не только список
категорий и `category_map`, но и саму историю в Google-таблице — старые
записи переезжают под новым именем (`sheets_transactions.rename_category_in_sheet`),
отчёты не разъезжаются.

## Установка

⚠️ В репозитории есть файл `.python-version` (закрепляет Python 3.12) —
не удаляй его. Без него Render на новых сервисах подхватывает самую свежую
версию Python, а для неё у некоторых зависимостей (`pydantic-core`, тянется
через `aiogram`) ещё нет готовых собранных пакетов — pip пытается собрать их
из исходников через Rust/Cargo, а песочница сборки на Render это запрещает,
деплой падает на этапе установки зависимостей. Если уже есть развёрнутый
сервис и появился этот файл впервые — на Render нужно **Clear build cache &
deploy**, обычного редеплоя может быть недостаточно (кеш от старой версии
Python).

⚠️ В `requirements.txt` версии зафиксированы как **минимальные** (`>=`), не
точные (`==`) — специально. Дважды за время разработки точная фиксация
приводила к рабочему падению не из-за нашего кода, а из-за того, что
зафиксированная версия SDK успевала устареть относительно внешнего сервиса
(Supabase сменил формат ключей — старый `supabase-py` не умел его
валидировать; Groq добавил параметр `reasoning_effort` — старый `groq` SDK о
нём не знал). `>=` даёт pip брать самую свежую совместимую версию при каждой
установке, что чаще спасает от такого дрейфа, чем ловит. **Не перезаписывай
эти строки обратно на `==`**, если не уверен, что именно должно быть жёстко
закреплено.

⚠️ **Render → Settings → Repository/Branch должны указывать ровно на тот
репозиторий и ветку, куда реально пушится код.** Если аккаунтов на GitHub
несколько — легко закоммитить в «не тот» репозиторий и потом долго не
понимать, почему изменения «не доходят» до бота при абсолютно рабочем коде.

```bash
python -m venv venv
source venv/bin/activate
pip install -r requirements.txt
cp .env.example .env  # заполнить токены
```

Выполнить `schema.sql` в Supabase SQL editor — метаданные
(users/категории/семья) плюс таблица `tx_mirror` (кэш-зеркало транзакций,
см. раздел «Хранение данных» ниже); сами транзакции туда не пишутся как
источник правды, только кэшируются.

### Переменные окружения (дополнительно к базовым)

- `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` — OAuth-клиент для Google Drive/
  Sheets (`drive.file` scope — этого достаточно для всех нужных методов
  Sheets API, Sensitive-скоуп не требуется)
- `GOOGLE_OAUTH_REDIRECT_URI` — свой домен, напр.
  `https://<этот-render-сервис>.onrender.com/oauth/callback`
- `CRON_SECRET` — произвольная строка; защищает `/cron/daily` от посторонних
  вызовов (см. ниже)
- `SHEETS_CACHE_TTL_SECONDS` (по умолчанию `60`) — TTL Redis-кэша чтения
  Sheets; `0` отключает этот кэш полностью
- `GROQ_TEXT_MODEL` / `GROQ_VISION_MODEL` / `GROQ_WHISPER_MODEL` —
  переопределить модели Groq без передеплоя кода, если текущая (см. ниже)
  будет депрекейтнута

### Ежедневный cron (напоминания + статистика + сверка кэша транзакций)

Настрой внешний пинг (UptimeRobot, как и для `/health`) раз в день на:
```
GET https://<этот-домен>.onrender.com/cron/daily?secret=<CRON_SECRET>
```
Один пинг закрывает три задачи, каждая сама решает, нужно ли что-то делать
именно сегодня:
- напоминание про пробег — раз в неделю на машину (трекается независимо для
  каждой)
- статистика — раз в отчётный период на пользователя (по его собственному
  дню начала периода, не календарный конец месяца)
- сверка `tx_mirror` (кэш-зеркало транзакций в Supabase) с реальным Google
  Sheets — по одному live-чтению на аккаунт-владелец; если число строк не
  совпало, зеркало сбрасывается и перегидрируется заново при следующем
  чтении (см. «Хранение данных» ниже)

### Устойчивость

- **Автоперезапуск polling** — если `dp.start_polling()` упадёт по сетевому
  сбою и т.п., бот сам перезапустит его через 5 сек, а не умрёт целиком
  (`run_polling_with_retry` в `main.py`).
- **Supabase keep-alive** — фоновая задача внутри бота стучится в Supabase
  каждые `SUPABASE_KEEPALIVE_INTERVAL_SECONDS` (по умолчанию 6 часов),
  независимо от внешних cron-пингов — free-tier проекты Supabase
  приостанавливаются после ~7 дней без обращений к API.
- **Google-токен** — `google_api.py` сам обновляет истёкший access token и
  повторяет запрос один раз, а не роняет операцию с 401.
- **Google Sheets 429/5xx** — те же вызовы автоматически повторяются с
  нарастающей паузой (`config.GOOGLE_TRANSIENT_RETRY_DELAYS`), вместо того
  чтобы либо зависать на минуты (нет таймаута), либо падать с первой же
  временной ошибки.
- **Кэш-зеркало транзакций (`tx_mirror`)** — после первой гидратации
  `/report`/`/history`/`/undo`/вопросы читают из Supabase, а не дёргают
  Sheets API на каждое действие; при записи зеркало обновляется тем же
  вызовом. Если Supabase на секунду недоступен именно в момент обновления
  зеркала — запись в Sheets всё равно проходит, зеркало просто останется
  на секунду устаревшим до следующей сверки/`/resync`. Расхождение
  обнаруживается и само чинится ежедневной сверкой (см. выше) или вручную
  командой `/resync`.
- **Защита от дублей** — повторный тап на «Записать» или повторно
  доставленный Telegram-апдейт в течение 120 секунд с той же суммой/
  комментарием/автором не создаёт вторую одинаковую запись
  (`tx_logic.find_recent_duplicate`).

Запуск:

```bash
python main.py
```

## Хранение данных

- **Транзакции** (реальные траты/доходы) — источник правды в Google Sheets
  **владельца** (личная таблица пользователя, либо владельца семьи, если
  состоишь в `/family`). Листы: «Транзакции» (все траты/доходы), «Авто»
  (структурные авто-траты — машина/тип/описание/пробег), «Пробег» (история
  показаний), «Машины» (регистр). У «Транзакции» и «Авто» два последних
  столбца — «Количество»/«Единица» (см. выше); у старых таблиц, созданных
  до этой функции, физического заголовка может не быть — бот читает по
  позиции колонки из кода, а не по тексту в шапке, так что на работу это не
  влияет, только на то, что сам увидишь глазами в таблице (можно дописать
  заголовок руками, это чисто косметика).
- **Supabase/Postgres** — метаданные: пользователи, категории,
  `category_map` (выученные соответствия слово→категория), семья, Google
  OAuth токены. Плюс таблица `tx_mirror` — **не источник правды**, а
  read-кэш содержимого листа «Транзакции» для более быстрых и дешёвых
  (по числу вызовов Google API) `/report`/`/history`/`/undo`/вопросов;
  поддерживается в консистентности incremental-записями и ежедневной
  сверкой/`/resync` — см. «Устойчивость» выше.

## Функциональность

- Три способа ввода: текст, голос (Whisper), фото чека (Vision — только
  итоговая сумма, без построчного разбора — см. выше)
- Категоризация: жёсткие правила → память (`category_map`) → Groq LLM →
  (если всё ещё не ясно) — кнопки на выбор
- Вопросы на естественном языке — см. раздел выше (ровно 4 вида: сумма/
  количество/когда/пробег)
- `/report`, `/history`, `/categories`, `/family`, `/undo`, `/settings`,
  `/cars`, `/carstats`, `/resync` — у всех команд в меню Telegram эмодзи,
  легче находить нужный пункт с непривычки
- **`/history`** — под каждым днём итоговая строка «Расход: X, Доход: Y»;
  если чего-то за день не было — честно «0», а не пропуск строки
- **`/report`** — под текстом отчёта ряд кнопок с прошлыми отчётными
  периодами («10.07–10.08.26» и т.д., 6 последних); нажатие показывает
  отчёт за тот период тем же сообщением (без спама новыми). Помимо
  дохода/расхода/остатка ЗА ПЕРИОД, показывает баланс «на руках» —
  сумма, введённая при онбординге, плюс все доходы минус все расходы за
  всю историю (не привязано к отчётному периоду)
- Онбординг: валюта → день периода → сумма на руках (опц.) → Google Drive
  (обязательно) → машина(ы) (опц.)
- Семейный бюджет: общий кошелёк (одна Google-таблица на семью, владелец —
  инициатор `/family`), без расчёта «кто кому должен»
- Реакция 👍 вместо текстового подтверждения записи
- **Авто-траты**: категория «Авто» → отдельный лист с типом (Заправка/ТО/
  Ремонт/Прочее), машиной, пробегом, количеством/единицей; несколько машин
  на семью с дизамбигуацией через кнопки
- **Пробег без валюты**: «пробег опель 305000 км» — отдельная ветка
- **Еженедельные напоминания о пробеге** — по каждой машине, кнопка «Без
  изменений»
- **Отслеживание техжидкостей** — предупреждение при приближении к
  интервалу замены (масло/антифриз/тормозная жидкость/фильтр/свечи), с
  учётом синонимов в описании («охлаждающая жидкость» = антифриз)
- **`/cars`** — список машин с удалением (мягкий архив + выгрузка полной
  истории в отдельный файл), добавление новой
- **`/carstats`** — статистика по машине за текущий период; плюс
  автоматическая рассылка в последний день периода всем, кто делит таблицу
- **`/resync`** — принудительно сбросить и перечитать кэш-зеркало
  транзакций из Google-таблицы (см. «Устойчивость» выше)

## Не входит (бэклог)

Построчный разбор фото чека (сейчас распознаётся только итоговая сумма —
см. раздел «Фото чека» выше), отдельный `/find` как явная команда (сейчас
его функцию частично закрывают вопросы на естественном языке), экспорт
Excel/PDF отдельно от Sheets, графики в отчётах, регулярные платежи,
интеграции с банками, персонализация интервалов замены жидкостей под
конкретный двигатель, прогноз/экстраполяция трат до конца периода, подсчёт
числа покупок отдельно от суммы, средний чек, кластеризация похожих товаров
в группы, сравнение с предыдущим периодом, вопросы «сколько потратила
Настя» (фильтр по конкретному члену семьи — данные есть, но списка имён
участников семьи под рукой у LLM пока нет, надо отдельно собирать).

Коммуналка намеренно НЕ вынесена отдельным листом (в отличие от «Авто») —
для неё нет отдельной аналитики по товарам/деталям, только обычный
`Комментарий` без структурной схемы.

## Известные допущения / TODO перед продакшеном

- Модели Groq (см. `GROQ_TEXT_MODEL`/`GROQ_VISION_MODEL`/`GROQ_WHISPER_MODEL`
  в `.env` или дефолты в `groq_client.py`) — сверить актуальные названия в
  консоли Groq перед деплоем, Groq иногда депрекейтит модели без долгого
  предупреждения; при депрекейшене можно быстро подменить через
  переменные окружения без изменения кода.
- Reactions (`set_message_reaction`) требуют Bot API 7.0+.
- Для группы более 2 человек в `/family` схема уже поддерживает N
  участников, тестировать на 2 сначала.

  формулировки вопросов) — см. `DEVELOPER_GUIDE.md`, там расписано, что
  можно смело менять самому, а что — код, требующий понимания regex/логики.
